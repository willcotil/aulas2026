O que é o HTTP?

HTTP (HyperText Transfer Protocol) é o protocolo padrão da World Wide Web.

Camada: Reside na Camada de Aplicação (camada 7 do modelo OSI / camada 4 do modelo TCP/IP).

Objetivo: Permitir a transferência de documentos de hipertexto (HTML, imagens, JSON, vídeos, etc.) entre clientes (navegadores, apps) e servidores.

Modelo: Cliente-Servidor, sem estado (stateless), baseado em requisição e resposta.

2 / 22

O HTTP no Modelo OSI

Cada camada cuida de um aspecto da comunicação. O HTTP fica no topo:

7 - Aplicação (HTTP, HTTPS, FTP, DNS, SMTP)
6 - Apresentação
5 - Sessão
4 - Transporte (TCP, UDP)
3 - Rede (IP)
2 - Enlace
1 - Física

O HTTP delega o transporte confiável dos pacotes ao TCP. Ele apenas define o "idioma" da conversa.

Verbos HTTP (Métodos)

Cada verbo define a intenção da requisição. Em APIs REST, mapeiam o CRUD:

VerboSignificadoUso em APIs Web
GETSolicita dados sem alterá-losRead — buscar produtos, carregar perfil
POSTEnvia dados para criar algo novoCreate — cadastrar usuário, postar comentário
PUTSubstitui um recurso por completoUpdate — atualizar perfil inteiro
PATCHAtualiza parcialmente um recursoUpdate — alterar só o e-mail
DELETERemove um recursoDelete — apagar uma postagem
HEADComo GET, mas só retorna headersChecar se um recurso existe
OPTIONSPergunta o que o servidor permiteUsado em CORS pelo navegador

Ponte com Desenvolvimento Web: em frameworks como Express, Spring ou Django, cada rota é registrada vinculando um verbo + caminho a uma função do servidor.

A Resposta do Servidor

Para toda requisição, o servidor responde com um código de status de 3 dígitos:

GrupoSignificado
1xxInformativo (raro de ver na prática)
2xxSucesso! (200 OK, 201 Created, 204 No Content)
3xxRedirecionamento (301 Moved, 302 Found, 304 Not Modified)
4xxErro do Cliente (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found)
5xxErro do Servidor (500 Internal Error, 502 Bad Gateway, 503 Service Unavailable)

Regra prática: 4xx = "a culpa é sua", 5xx = "a culpa é do servidor".

O Problema do HTTP (1991)

O HTTP foi criado por Tim Berners-Lee em 1991, com um objetivo simples: trocar documentos científicos no CERN. Segurança não era prioridade.

Todo o tráfego HTTP circula em texto claro (plaintext). Isso significa que qualquer nó intermediário entre você e o servidor pode ler tudo que passa:

  • Seu provedor de internet (ISP)
  • O roteador Wi-Fi público da cafeteria
  • Qualquer pessoa "escutando" a rede

Senhas, números de cartão, mensagens privadas — tudo visível.

A Solução: HTTPS (1994)

Em 1994, a Netscape (criadora do navegador Netscape Navigator) introduziu o SSL (Secure Sockets Layer), depois evoluído para o TLS (Transport Layer Security).

HTTPS = HTTP + TLS. A ideia é simples e elegante: em vez de modificar o HTTP, encapsulá-lo dentro de um túnel criptografado.

HTTP puro

Mensagem visível para qualquer interceptador.

"senha=123456"

HTTPS

Mensagem cifrada, ilegível na rede.

"7a3f9c1e8d2b6f0a..."

O HTTP continua sendo a mesma linguagem; o que muda é o "envelope" que o transporta.

10 / 22

O Conceito de Túnel

Em redes, um túnel é uma técnica em que um protocolo é encapsulado dentro de outro, criando um "canal protegido" através de uma rede pública.

Analogia: imagine que você precisa entregar uma carta atravessando uma cidade cheia de gente curiosa. Sem túnel, sua carta vai numa bandeja aberta — todo mundo lê. Com um túnel, você passa por baixo da cidade, dentro de um corredor blindado: as pessoas até veem que algo está sendo transportado, mas não conseguem ver o quê.

No HTTPS, o "túnel" é o TLS: ele envolve o HTTP de ponta a ponta, do navegador até o servidor. Tudo que entra no túnel é cifrado; tudo que sai é decifrado.

Para o desenvolvedor, nada muda: ele escreve o mesmo HTTP. Navegador e servidor cuidam de montar o túnel automaticamente.

O que é Criptografia?

Criptografia é a arte de transformar uma mensagem legível em algo ilegível, de modo que apenas quem tem a "chave" possa voltar à mensagem original.

Simétrica

Uma única chave cifra e decifra. Rápida, mas há um problema: como entregar essa chave em segurança?

Exemplo: AES.

Assimétrica

Duas chaves matematicamente ligadas: uma pública e uma privada. Resolve o problema da entrega da chave.

Exemplo: RSA, ECDSA.

O HTTPS usa as duas: assimétrica para trocar uma chave simétrica com segurança, depois simétrica para o resto da conversa (porque é mais rápida).

12 / 22

Chave Pública vs Chave Privada

Como duas chaves diferentes podem cifrar e decifrar a mesma mensagem? A matemática por trás (números primos enormes) garante uma relação especial:

  • O que é cifrado com a chave pública só pode ser decifrado com a chave privada correspondente.
  • A chave pública pode ser compartilhada livremente com o mundo todo.
  • A chave privada nunca sai do servidor que a criou.

Analogia do cadeado: imagine que o servidor distribui milhões de cadeados abertos (chave pública). Qualquer um pode pegar um cadeado, colocar uma mensagem numa caixa e fechá-la. Mas só o servidor tem a chave que abre aquele cadeado (chave privada).

Autoridades Certificadoras (CAs)

Mas espera: como meu navegador sabe que aquela chave pública é realmente do Google, e não de um impostor?

Uma Autoridade Certificadora (CA) é uma empresa (não um governo) de confiança internacional que assina digitalmente certificados, atestando que "a chave pública X pertence ao site Y".

Exemplos de CAs conhecidas:

  • Let's Encrypt — gratuita, sem fins lucrativos (ISRG)
  • DigiCert — uma das maiores comerciais
  • GlobalSign, Sectigo, GoDaddy — outras opções pagas

No Brasil, o ICP-Brasil é uma infraestrutura governamental de certificação, mas para HTTPS na web usamos as CAs internacionais.

A Tríade CIA da Segurança

Em segurança da informação, três princípios devem ser protegidos. O HTTPS atende aos três:

C
Confidencialidade

Apenas as partes autorizadas leem a mensagem.

→ Criptografia TLS

I
Integridade

A mensagem não foi alterada no caminho.

→ Hashes (MAC/HMAC)

A
Autenticidade

Você fala com quem diz ser, não com um impostor.

→ Certificado da CA

A tríade CIA é aplicada também em VPNs, e-mails seguros (PGP), assinatura digital de documentos, sistemas bancários e qualquer canal que precise de segurança real.

Principais Ameaças (1/2)

AmeaçaComo funcionaMitigação
Phishing Sites/e-mails falsos imitam serviços legítimos para roubar credenciais. Educação do usuário, verificar URL, 2FA, filtros anti-phishing no e-mail.
Man-in-the-Middle (MITM) Atacante se posiciona entre cliente e servidor para interceptar tráfego. HTTPS obrigatório, HSTS, certificados válidos, VPN em redes públicas.
SQL Injection Atacante injeta comandos SQL em formulários para manipular o banco de dados. Prepared Statements, validação e sanitização de entrada, ORM seguro.
XSS (Cross-Site Scripting) Injeção de JavaScript malicioso em páginas que outros usuários carregam. Sanitização do output, Content Security Policy (CSP), escapar HTML.
CSRF Faz o navegador da vítima executar ações em um site onde ela está logada. Tokens CSRF, atributo SameSite em cookies, validação de Origin/Referer.

Principais Ameaças (2/2)

AmeaçaComo funcionaMitigação
DDoS Milhares de máquinas inundam o servidor de requisições até derrubá-lo. WAF, rate limiting, CDN com proteção (Cloudflare), escalabilidade.
Força Bruta Testa milhares de senhas até acertar a do usuário. Senhas fortes, bloqueio após N tentativas, 2FA, CAPTCHAs.
Sequestro de Sessão Atacante rouba o cookie de sessão e finge ser o usuário. HTTPS, cookies Secure + HttpOnly + SameSite, expiração curta.
DNS Spoofing Atacante envenena cache de DNS para redirecionar a vítima a um site falso. DNSSEC, DNS sobre HTTPS (DoH), verificação de certificado HTTPS.
Engenharia Social Manipulação psicológica da vítima para revelar dados ou agir contra si. Treinamento de equipe, políticas claras, princípio do menor privilégio.

Boas Práticas Resumidas

  • Sempre use HTTPS (HSTS + redirecionamento automático de HTTP → HTTPS).
  • Mantenha certificados atualizados (Let's Encrypt renova automaticamente).
  • Nunca confie na entrada do usuário — sempre valide e sanitize.
  • Use 2FA em todos os serviços críticos.
  • Cookies sensíveis sempre com flags Secure, HttpOnly e SameSite.
  • Cabeçalhos de segurança: CSP, X-Frame-Options, X-Content-Type-Options.
  • Atualize dependências — bibliotecas desatualizadas têm CVEs conhecidos.

Recapitulando

HTTP

  • Camada de aplicação
  • Verbos: GET, POST, PUT, DELETE...
  • Status: 2xx, 3xx, 4xx, 5xx
  • Headers carregam metadados
  • Texto claro → inseguro

HTTPS

  • HTTP encapsulado em TLS
  • Chaves pública e privada
  • Certificado assinado por uma CA
  • Garante Confidencialidade, Integridade e Autenticidade
  • Padrão obrigatório na web moderna

HTTPS não é opcional em 2026 — é o piso.
