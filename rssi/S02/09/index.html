Recapitulando

O Que Vamos Praticar Hoje

A Aula 8 explicou firewall, IDS/IPS e VPN na teoria. Hoje é dia de colocar a mão: vamos voltar pro MESMO ambiente da demonstração da Aula 4 — só que, em vez de assistir o professor atacar e defender, é você quem vai configurar as duas defesas de verdade.

O que já sabemos (Aula 8)

  • Firewall decide por uma lista de regras — a primeira que casa vence
  • Stateful: o firewall lembra sozinho as conexões já estabelecidas
  • VPN cria um túnel criptografado sobre uma rede pública
  • Na Aula 4, o MITM capturou uma senha em texto puro via HTTP

Objetivo 1: Firewall

Fazer o SYN flood da Aula 4 parar de derrubar o serviço, de verdade, com uma regra que você mesmo escreve.

Objetivo 2: VPN

Fazer o MITM da Aula 4 continuar funcionando, mas capturar só bytes ilegíveis.

Preparando o Ambiente

A mesma topologia Docker da Aula 4, agora no seu comando

Preparando a Imagem Docker

A imagem de hoje é a mesma Kali Linux com ferramentas de rede da Aula 4 (Dockerfile.rssi-lab) — só que agora com o wireguard-tools também instalado. Reconstrua a imagem a partir do Dockerfile atualizado:

Dockerfile.rssi-lab
FROM kalilinux/kali-rolling
RUN apt-get update && apt-get install -y \
    bash iproute2 iptables tcpdump hping3 dsniff net-tools iputils-ping busybox-static curl dnsmasq procps wireguard-tools \
    && rm -rf /var/lib/apt/lists/*
docker build -t rssi-lab:kali -f Dockerfile.rssi-lab .

Por que :kali, e não :latest

A tag segue o mesmo nome já usado na Aula 4 (rssi-lab:kali) — assim é a MESMA imagem sendo reaproveitada entre as aulas, em vez de uma tag nova (:latest) que o Docker tentaria baixar de um repositório que não existe.

A Mesma Topologia da Aula 4

Mesmos três containers da demonstração — vitima (10.10.10.20), atacante (10.10.10.10) e servico (10.10.10.53) — nos MESMOS IPs fixos do setup.sh da Aula 4, na mesma rede rssi-labnet. Assim os scripts prontos (ddos.sh, mitm.sh) continuam funcionando sem precisar editar nada.

# Se a rede/containers da Aula 4 ainda estiverem de pé, derrube primeiro:
docker rm -f vitima atacante servico 2>/dev/null
docker network rm rssi-labnet 2>/dev/null

docker network create --driver bridge --subnet 10.10.10.0/24 rssi-labnet

docker run -dit --name servico --network rssi-labnet --ip 10.10.10.53 \
  --cap-add=NET_ADMIN --cap-add=NET_RAW --device=/dev/net/tun \
  --sysctl net.ipv4.tcp_syncookies=0 \
  rssi-lab:kali

docker run -dit --name vitima --network rssi-labnet --ip 10.10.10.20 --dns 1.1.1.1 \
  --cap-add=NET_ADMIN --cap-add=NET_RAW --device=/dev/net/tun \
  --sysctl net.ipv4.tcp_syncookies=0 \
  --sysctl net.ipv4.conf.all.arp_accept=1 \
  --sysctl net.ipv4.conf.default.arp_accept=1 \
  rssi-lab:kali

docker run -dit --name atacante --network rssi-labnet --ip 10.10.10.10 \
  --cap-add=NET_ADMIN --cap-add=NET_RAW \
  --sysctl net.ipv4.tcp_syncookies=0 \
  --sysctl net.ipv4.ip_forward=0 \
  rssi-lab:kali

# Mesmo site falso do setup.sh, escutando no servico
docker exec servico sh -c "ss -ltn | grep -q ':80'" \
  || docker exec -d servico busybox httpd -f -p 80 -h /tmp

NET_RAW, além de NET_ADMIN, nos TRÊS containers

Diferente da Aula 4 (onde servico era só um alvo passivo), hoje servico TAMBÉM roda wg-quick up wg0 — e isso exige NET_ADMIN pra criar a interface WireGuard. Por isso os TRÊS containers (não só vitima/atacante) precisam de --cap-add=NET_ADMIN --cap-add=NET_RAW hoje.

Mesma rede, com internet de propósito

Essa rede NÃO é isolada (--internal) — é a MESMA bridge com saída real pra internet que a Aula 4 já usava, de propósito: é isso que permite ao mitm.sh interceptar a consulta DNS real da vitima pro www.google.com, exatamente como na demonstração.

Confirmando Que Está Tudo de Pé

docker exec vitima ping -c 2 10.10.10.10
docker exec vitima ping -c 1 www.google.com

Lembrando da ética da Aula 4

A rede tem saída pra internet de propósito, só pra vitima conseguir pingar o www.google.com de verdade — as ferramentas de ataque (arpspoof, dnsspoof, hping3) só enxergam e só afetam essa rede isolada entre os containers; a única coisa que realmente sai daqui é um ping comum, sem nenhum ataque envolvido. O mesmo cuidado que abriu a Aula 4 (Lei 12.737/2012).

Firewall na Prática

iptables de verdade, mitigando o SYN flood da Aula 4

Hoje o servico Está Totalmente Aberto

Por padrão, servico ainda não tem NENHUMA regra de firewall — política ACCEPT geral. Vamos confirmar que o MESMO ataque da Aula 4 ainda funciona antes de defender.

no atacante
docker exec atacante timeout 5 hping3 -S --flood -p 80 servico

Por que a tela do atacante fica em branco

Em modo --flood, o hping3 propositalmente NÃO imprime nada por pacote — é isso que permite mandar pacotes o mais rápido possível, sem gastar tempo escrevendo na tela. Fica rodando em silêncio por 5 segundos (o timeout 5) e termina sozinho, sem erro nenhum.

no servico, em outro terminal, ao mesmo tempo
docker exec servico timeout 5 tcpdump -i eth0 -n 'tcp[tcpflags] & tcp-syn != 0 and dst port 80'

Isso é a prova de que o ataque chegou

Essa segunda janela mostra uma enxurrada de pacotes SYN chegando no servico — é ESSA tela que confirma o ataque, não a do atacante. Exatamente o que vimos na Aula 4, antes da mitigação ao vivo do professor.

Regra 1: Negar Tudo por Padrão

Em vez de tentar bloquear cada coisa ruim uma a uma (lista de bloqueio), a boa prática é inverter: negar tudo por padrão e liberar só o que for explicitamente necessário (lista de permissão) — assim, nada passa por descuido.

no servico
# Política padrão: se NENHUMA regra abaixo casar, o pacote é DESCARTADO (nega por padrão)
iptables -P INPUT DROP
iptables -P FORWARD DROP

# Sempre libera o tráfego da interface local (loopback, 127.0.0.1) -- processos
# internos do próprio servico dependem disso pra se comunicar entre si
iptables -A INPUT -i lo -j ACCEPT

# Libera direto as RESPOSTAS de conexões que o servico MESMO iniciou ou já aceitou
# antes (ESTABLISHED = conexão em andamento, RELATED = relacionada a uma, ex: erro ICMP)
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

Por que a regra stateful vem logo no início

ESTABLISHED,RELATED (Aula 8) deixa passar direto as RESPOSTAS de conexões que o próprio servico já aceitou antes — sem ela, nem o tráfego legítimo voltaria.

Regra 2: Liberando Só o Essencial

no servico (continuando)
# Libera ping (ICMP echo-request) -- útil pra testar conectividade
iptables -A INPUT -p icmp --icmp-type echo-request -j ACCEPT

# Libera só pacotes NOVOS (--syn = início de conexão) na porta 80,
# limitando a 1 por segundo (--limit-burst 3 permite uma rajada inicial de
# até 3 antes do limite valer pra valer)
iptables -A INPUT -p tcp --dport 80 --syn \
  -m limit --limit 1/s --limit-burst 3 -j ACCEPT

"A primeira regra que casa vence" (Aula 8)

Essa última regra só aceita um NOVO pacote SYN na porta 80 até 1 por segundo (com rajada de 3). Não precisamos de mais nenhuma regra pra porta 80: o tráfego de uma conexão já aberta cai na regra ESTABLISHED,RELATED de cima, e qualquer SYN que passar do limite simplesmente não casa com nenhuma regra — e cai na política padrão DROP.

Retestando o Ataque

docker exec atacante timeout 5 hping3 -S --flood -p 80 servico

# em outro terminal, observando os contadores da regra:
docker exec servico iptables -L INPUT -v --line-numbers

VPN na Prática

Túnel WireGuard protegendo o MITM da Aula 4

WireGuard: um Túnel Simples de Configurar

WireGuard é um software de VPN moderno e minimalista: implementa o conceito de túnel criptografado da Aula 8 usando a MESMA ideia de par de chaves pública/privada da criptografia assimétrica da Aula 6.

docker exec vitima sh -c "mkdir -p /etc/wireguard && wg genkey | tee /etc/wireguard/privatekey | wg pubkey > /etc/wireguard/publickey"

docker exec servico sh -c "mkdir -p /etc/wireguard && wg genkey | tee /etc/wireguard/privatekey | wg pubkey > /etc/wireguard/publickey"

Cada lado guarda a privada e entrega a pública

vitima e servico geram seu PRÓPRIO par de chaves. A chave privada nunca sai de onde foi gerada; só a chave pública é compartilhada com o outro lado — exatamente como na Aula 6.

Por que o mkdir -p primeiro

A imagem Kali não cria /etc/wireguard/ sozinha ao instalar o wireguard-tools — sem essa pasta, o tee falha em silêncio tentando salvar a chave privada ali (a pública ainda é gerada normalmente, porque sai por outro redirecionamento). Por isso criamos a pasta ANTES de gerar as chaves.

Montando o Arquivo de Configuração

O wg0.conf fica DENTRO de cada container, nunca na sua máquina — são DOIS arquivos diferentes (/etc/wireguard/wg0.conf em vitima e em servico), cada um só com a configuração dele. Como a imagem não tem editor de texto instalado, escrevemos o conteúdo de fora com docker exec -i + heredoc.

# Captura as chaves PÚBLICAS dos dois lados, pra montar os arquivos abaixo
PUB_SERVICO=$(docker exec servico cat /etc/wireguard/publickey)
PUB_VITIMA=$(docker exec vitima cat /etc/wireguard/publickey)

# Escreve o wg0.conf DENTRO do container servico
# (a chave PRIVADA é lida de dentro do próprio container, nunca sai dele)
docker exec -i servico sh -c "cat > /etc/wireguard/wg0.conf" <<EOF
[Interface]
Address = 10.0.9.1/24
PrivateKey = $(docker exec servico cat /etc/wireguard/privatekey)
ListenPort = 51820

[Peer]
PublicKey = $PUB_VITIMA
AllowedIPs = 10.0.9.2/32
EOF

# Escreve o wg0.conf DENTRO do container vitima
docker exec -i vitima sh -c "cat > /etc/wireguard/wg0.conf" <<EOF
[Interface]
Address = 10.0.9.2/24
PrivateKey = $(docker exec vitima cat /etc/wireguard/privatekey)

[Peer]
PublicKey = $PUB_SERVICO
Endpoint = 10.10.10.53:51820
AllowedIPs = 10.0.9.1/32
EOF

Por que heredoc, e não um editor

A imagem não tem nano/vim instalados. Rodar docker exec -i <container> sh -c "cat > arquivo" e mandar o conteúdo por um heredoc (<<EOF ... EOF) é a forma mais direta de criar um arquivo dentro de um container sem precisar instalar nada a mais — o -i mantém a entrada aberta pro heredoc chegar até lá.

AllowedIPs e Endpoint

AllowedIPs diz quem pode falar com quem DENTRO do túnel; Endpoint diz pra vitima onde encontrar o servico de fora do túnel (o IP real 10.10.10.53 da rede bridge), pra iniciar a conexão.

Subindo o Túnel e Confirmando o Handshake

docker exec servico wg-quick up wg0
docker exec vitima wg-quick up wg0

docker exec vitima wg show

O que confirma que deu certo

Um latest handshake recente na saída do wg show confirma que os dois lados se autenticaram com as chaves e o túnel está de pé.

Recapitulando: O Que Acabamos de Montar

Antes de testar a VPN contra o MITM, vale parar e entender o que esses comandos realmente fizeram — e como isso se conecta ao que já vimos nas Aulas 6 e 8.

Qualquer acesso que a vitima fizer pro IP 10.0.9.1 (em vez do 10.10.10.53) passa a viajar DENTRO do túnel, cifrado, antes de sair pra rede real.

As chaves que geramos, e a conexão com a Aula 6

Cada lado (vitima e servico) gerou seu PRÓPRIO par de chaves assimétricas (wg genkey/wg pubkey) — a mesma ideia de chave pública/privada da criptografia assimétrica da Aula 6. Só que, igual ao modelo híbrido do HTTPS/TLS (também Aula 6), essas chaves de longo prazo só servem pra AUTENTICAR os dois lados no handshake inicial; o tráfego de verdade, depois disso, é cifrado com uma chave de sessão simétrica — bem mais rápida, a mesma lógica de "assimétrica só pra combinar a chave, simétrica pra cifrar o volume".

Conectando com a Aula 8

Isso é exatamente o conceito de túnel criptografado sobre uma rede pública que a Aula 8 introduziu como VPN — só que agora configurado por vocês, com WireGuard, entre dois containers reais.

Refazendo o MITM da Aula 4 — Agora Com VPN

Precisa de DOIS terminais ao mesmo tempo: um com o atacante escutando, outro com a vitima mandando a MESMA requisição de login da Aula 4 — só que agora PELO TÚNEL.

terminal 1: no atacante
docker exec atacante sh -c \
  "arpspoof -i eth0 -t 10.10.10.20 10.10.10.53 >/dev/null 2>&1 & timeout 20 tcpdump -i eth0 -n -A udp port 51820"
terminal 2: na vitima, ENQUANTO o terminal 1 roda
docker exec vitima curl "http://10.0.9.1/login?usuario=aluno&senha=SenhaSecreta123"

O ARP spoofing funciona. A senha, não.

O tcpdump do terminal 1 mostra uma enxurrada de bytes ilegíveis no exato momento em que o curl do terminal 2 roda — o ARP spoofing AINDA coloca o atacante no meio do caminho físico, mas a requisição foi pro IP do túnel (10.0.9.1), então ela já saiu cifrada da vitima antes de entrar na rede. Compare com a Aula 4, onde a mesma linha GET /login?usuario=... aparecia em texto puro.

Limpando depois

O arpspoof fica rodando em segundo plano no atacante até o timeout do tcpdump (20s) terminar o comando todo. Se quiser encerrar antes: docker exec atacante pkill arpspoof.

Defesa em camadas, na prática

Nenhuma defesa sozinha resolveu tudo: o firewall não impede o MITM, e a VPN não impede o ARP spoofing. Juntas, cada uma cobre o que a outra deixa passar — o conceito de defesa em camadas da Aula 8, agora comprovado na prática.
