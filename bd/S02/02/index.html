Relembrando a Aula 1

1FN e 2FN antes de completar com a 3FN

Slide 02

Onde Paramos

1FN

Toda célula guarda um único valor atômico — sem grupos repetidos, sem listas escondidas numa coluna.

2FN

Todo atributo não-chave depende da chave primária inteira — nunca só de uma parte dela, quando a chave é composta.

Mas ainda falta algo...

Mesmo depois da 2FN, um atributo pode depender de OUTRO atributo que também não é chave — e essa redundância escondida é o que a 3FN resolve hoje.

Terceira Forma Normal (3FN)

Eliminando a dependência transitiva

Slide 03

A Ideia por Trás da 3FN

Pensa num jogo online com sistema de ligas: seu ID de jogador determina sua liga (Bronze, Prata, Ouro...) depois de você farmar pontos a temporada toda. E é a liga — não o seu ID — que determina o prêmio de fim de temporada.

flowchart LR A["ID do jogador"] --> B["Liga (Bronze, Prata, Ouro...)"] B --> C["Prêmio de fim de temporada"]

Isso é uma dependência transitiva

O prêmio não depende do seu ID diretamente — depende da liga, que por sua vez depende do ID. Numa tabela, isso é sinal de que falta separar mais uma entidade.

Slide 04

Pré-Requisito e Regra da 3FN

Quando a 3FN se aplica?

Só faz sentido avaliar a 3FN em tabelas que já estão na 2FN. Sem isso, ainda pode sobrar dependência parcial disfarçada de transitiva.

A regra

Todo atributo que não faz parte da chave deve depender apenas da chave primária — nunca de outro atributo que também não é chave. Depender de um atributo não-chave é chamado de dependência transitiva.

Slide 05

O Problema: Dependência Transitiva

Uma bilheteria online guarda os ingressos vendidos numa única tabela, repetindo os dados do evento em cada linha:

ingresso (fora da 3FN)
ingresso_idcompradorevento_idnome_eventolocal_evento
1Rafael Nunes500Festival BatidasAllianz Parque
2Camila Rocha500Festival BatidasAllianz Parque
3Rafael Nunes501Turnê ElétricaEspaço das Américas

O sintoma

  • nome_evento não depende da chave.
  • local_evento também não depende da chave.
  • Os dois dependem de evento_id, que também não é chave.
  • Isso é dependência transitiva: a chave aponta pro evento, e é o evento que determina esses dados.

Tudo que depende só de evento_id vira sua própria tabela; ingresso fica só com o que realmente depende da sua chave:

Slide 15

Aplicando o Checklist da 3FN

Rodando o checklist de hoje na tabela aluno: existe algum atributo que depende de outro atributo que não é a chave?

O gatilho: dependência transitiva

  • curso nome depende de curso_id — não do aluno, que é a chave.
  • Isso é dependência transitiva: curso_id mora na tabela aluno, mas curso nome deveria morar junto do curso.

E o professor, não deveria sair também?

professor depende diretamente de disciplina_id — a própria chave da tabela disciplina. Não é dependência transitiva, então ele fica onde está.

Slide 16

Decomposição Final (3FN)

matricula → aluno + curso + disciplina
erDiagram CURSO ||--o{ ALUNO : possui ALUNO ||--o{ MATRICULA : faz DISCIPLINA ||--o{ MATRICULA : recebe CURSO { int curso_id PK string curso_nome } ALUNO { int aluno_id PK string aluno_nome int curso_id FK } DISCIPLINA { int disciplina_id PK string disciplina_nome string professor } MATRICULA { int aluno_id FK int disciplina_id FK }

Zero redundância

  • curso nome mora só na tabela curso.
  • disciplina nome e professor moram só na tabela disciplina.
  • Eles ficam lá porque dependem diretamente de disciplina_id — não é dependência transitiva.
