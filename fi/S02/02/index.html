Começando do Zero

git init e o que fica de fora da linha do tempo

Slide 03

git init: criando o repositório

Na Aula 1 você já viu commit e add — mas de onde vem o repositório em si? git init transforma uma pasta comum numa pasta que o Git passa a vigiar.

O que git init faz
flowchart LR A["Pasta comum\n(sem controle de versao)"] -->|git init| B["Mesma pasta\n+ pasta oculta .git/"] B --> C["Pronta pra registrar\ncommits"]
terminal
mkdir portfolio-pessoal
cd portfolio-pessoal
git init

# a pasta .git/ guarda TODO o historico
ls -la
# .git  (nao mexa manualmente aqui dentro)
Slide 04

.gitignore: nem tudo vira página da linha do tempo

Rascunho pessoal, senha, pasta de backup automático... tem arquivo que não faz sentido (ou é perigoso) versionar. O .gitignore diz pro Git "finge que isso aqui não existe".

.gitignore
# arquivos e pastas que o Git vai ignorar
anotacoes-privadas.txt
backup/
*.tmp

Dica de ferramenta

Pedir pra uma IA sugerir um .gitignore pronto pro tipo do seu projeto é um baita atalho — só sempre dê uma conferida se o que ela sugeriu faz sentido pro SEU caso antes de aceitar de olhos fechados.

  • Arquivos com dado sensível (senha, chave)
  • Pastas geradas automaticamente (backup, cache)
  • Arquivos temporários do editor/sistema

Radar de Mudanças

Botando o git diff pra trabalhar de verdade

Slide 05

Onde o diff entra nos três estados

Lembra dos três estados da Aula 1 — modified, staged, committed? O git diff é a lupa que mostra exatamente o que muda entre um estado e outro.

git diff nos três estados
flowchart LR WD["Working Directory\n(o que voce edita)"] -->|git add| ST["Staging Area\n(area de stage)"] ST -->|git commit| REPO["Repositório\n(commits salvos)"] WD -->|git diff| ST ST -->|git diff --staged| REPO

Dois comandos, dois comparativos

  • git diff → compara o arquivo editado com o que está staged (ou o último commit, se nada foi staged)
  • git diff --staged → compara o que está staged com o último commit
Slide 06

git diff na prática

terminal
# editou estilo.css e quer ver o que mudou antes de commitar
git diff

--- a/estilo.css
+++ b/estilo.css
@@ -1,3 +1,3 @@
 body {
-  background: white;
+  background: #0b192c;
 }

# depois de git add, o comparativo muda de alvo
git add estilo.css
git diff --staged
# mostra a MESMA mudanca, mas agora comparando com o ultimo commit

Lendo o diff

Linha com - é o que existia antes e saiu. Linha com + é o que entrou. Se o git diff não mostrar nada, é porque não há mudança pendente pra esse arquivo naquele estado.

Múltiplos Arquivos, Um Commit

git add em lote e o fluxo real de trabalho

Slide 07

git add: um por um, ou tudo de uma vez

terminal
# um arquivo por vez
git add index.html

# varios de uma vez, nomeando cada um
git add index.html estilo.css

# todo mundo que ja e rastreado + novos, na pasta atual pra baixo
git add .

# a pasta inteira do repositorio, mesmo fora da pasta atual
git add -A
Qual usar?
ComandoO que pegaCuidado
git add .Novos e modificados, da pasta atual pra baixoNão sobe pra pastas acima da atual
git add -ATudo no repositório inteiro (inclusive delеções)Fácil adicionar algo sem querer — confira com git status antes
git add arquivoSó o que você nomearMais controle, mais digitação
Slide 08

Simulação: criando um repositório do zero (Parte 1)

Você vai começar o repositório do seu portfólio pessoal. Acompanhe a sequência de comandos como se estivesse no seu próprio terminal.

terminal
git init
touch index.html estilo.css anotacoes-privadas.txt

# cria o .gitignore com anotacoes-privadas.txt dentro

git status
# Untracked: .gitignore, estilo.css, index.html
# (anotacoes-privadas.txt nao aparece: esta ignorado)

git add index.html estilo.css .gitignore
git commit -m "Cria estrutura inicial do portfolio (HTML e CSS)"
Slide 09

Simulação: criando um repositório do zero (Parte 2)

Agora você edita o CSS e repete o ciclo — só que dessa vez conferindo a mudança com diff antes de commitar.

terminal
# editou o estilo.css, mudou a cor de fundo

git diff
# mostra a mudanca ainda so no working directory

git add estilo.css
git diff --staged
# mesma mudanca, agora comparada com o ultimo commit

git commit -m "Ajusta cor de fundo do portfolio"

git log --oneline
# a1b2c3d Ajusta cor de fundo do portfolio
# f9e8d7c Cria estrutura inicial do portfolio (HTML e CSS)

Mensagens Que Contam a História Direito

convenção de commit: o que ajuda e o que atrapalha

Slide 10

Mensagem de commit: ajuda ou atrapalha?

Mensagens ruins

  • "six seven"
  • "wip"
  • "fix"
  • "asdasd"
  • "mudei umas coisas"

Mensagens boas

  • "Corrige bug de login com senha vazia"
  • "Adiciona validação de e-mail no cadastro"
  • "Remove import não usado no header"
  • "Cria estrutura inicial do portfolio"

A convenção

Verbo no imperativo (Corrige, Adiciona, Remove), resumo curto e específico o bastante pra você entender daqui 6 meses — sem precisar abrir o git diff pra lembrar o que fez.

Slide 11

git log: opções que economizam tela

Você já usou git log na Aula 1 pra ver o histórico completo. Um projeto real tem dezenas (ou milhares) de commits — hora de compactar.

terminal
git log --oneline
# a1b2c3d Ajusta cor de fundo do portfolio
# f9e8d7c Cria estrutura inicial do portfolio (HTML e CSS)

git log --oneline -n 1
# so o commit mais recente

git log --oneline --author="Maria"
# so os commits de uma pessoa (util em Aula 4, com equipe)

--oneline é seu melhor amigo

Reduz cada commit a uma linha: hash curto + mensagem. É o formato que a maioria dos devs usa no dia a dia pra não perder tempo rolando tela.

Ops, Errei o Commit

corrigindo o último ponto da linha do tempo

Slide 12

git commit --amend

Escreveu a mensagem errada ou esqueceu de adicionar um arquivo no último commit? Em vez de criar mais um commit só pra corrigir, você reescreve o último ponto da linha do tempo.

terminal
# corrigir so a mensagem do ultimo commit
git commit --amend -m "Cria estrutura inicial do portfolio"

# esqueceu um arquivo? adiciona e reaproveita a mesma mensagem
git add index.html
git commit --amend --no-edit

Cuidado: isso reescreve a história

Não fica commitando 10 vezes só pra ajustar um detalhezinho — isso não farma nenhuma aura no histórico, só polui o log. Use --amend antes de compartilhar o projeto com alguém (isso é papo pra Aula 3, com GitHub). Depois de publicado, reescrever vira dor de cabeça pra quem já baixou.

Desafios

Desafios

  1. Crie uma pasta nova, rode git init e confirme que apareceu a pasta oculta .git.
  2. Crie 3 arquivos à sua escolha e um .gitignore que ignore pelo menos um deles.
  3. Faça 3 commits com mensagens boas, mudando algo diferente em cada um.
  4. Entre um git add e um git commit, use git diff e git diff --staged pra comparar.
  5. Rode git log --oneline e confira o histórico compacto do seu projeto.
  6. Erre de propósito uma mensagem de commit e conserte com git commit --amend.
